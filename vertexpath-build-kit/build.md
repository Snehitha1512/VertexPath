## 2. Decisions already made (do not re-litigate)

1. **Backend: keep Supabase, but a NEW project in Snehitha's own Supabase account.** Not Lovable Cloud (its database can't be opened in the Supabase dashboard and can't be switched later). Postgres + Auth + Storage + Edge Functions + pg_cron all fit this app; no other database is needed.
2. **Dev flow:** code lives in the GitHub repo and is edited in Antigravity. Lovable is not used for edits any more (two tools editing one repo causes merge conflicts). Hosting can be Lovable Publish, Vercel or Netlify; out of scope here.
3. **LinkedIn:** supported only through *user-initiated* imports: (a) LinkedIn's official data export (`Certifications.csv`, `Projects.csv`), (b) text from LinkedIn's "Save to PDF" profile or a resume PDF, extracted by AI, (c) manual entry. Every import goes to a **review queue**; nothing is added silently.
4. **Automatic 2–3 day sync:** implemented for **GitHub public repos only** (official API, allowed), landing in the same review queue. Optional, Phase 6.
5. **AI:** called only from the Edge Function `ai-assist` (already written, in `supabase/functions/ai-assist/index.ts`). Provider is switchable via the `AI_PROVIDER` secret (`gemini` default, or `anthropic`). Frontend never sees a key.
6. **Ranking:** deterministic scoring in the frontend (explainable, free, instant). AI only rewrites text; it does not decide ranking.
7. **PDF:** `@react-pdf/renderer` (real selectable text, ATS-friendly; image-based PDFs from html2canvas are not).
8. **Resumes are JSON snapshots** in `resumes.content`, so editing a resume never changes the original project/certification.

## 8. Data shape (resume snapshot)

```ts
type ResumeItem = {
  kind: 'project' | 'certification';
  sourceId: string;            // projects.id / certifications.id at the time of adding
  title: string;               // editable copy
  subtitle?: string;           // issuer, or technologies joined
  bullets: string[];           // editable copy (projects)
  date?: string;
  url?: string;
};
type ResumeContent = {
  summary: string;
  skills: string[];
  projects: ResumeItem[];      // order = display order
  certifications: ResumeItem[];
  hiddenSections?: string[];
};
```

## 9. Ranking spec (`ranking.ts`, `roles.ts`)

`roles.ts` exports ~10 roles (Full-Stack Developer, Frontend Developer, Backend Developer, Cybersecurity Analyst, AI/ML Engineer, Data Analyst, Data Scientist, Cloud/DevOps Engineer, Mobile Developer, QA Engineer), each with weighted keyword lists, e.g.:

```ts
'Cybersecurity Analyst': {
  core:  ['security','malware','threat','vulnerability','incident response','siem','penetration','forensic','network security'],
  tech:  ['python','wireshark','nmap','metasploit','splunk','linux','burp'],
  adjacent: ['machine learning','networking','cloud','cryptography']
}
```

Score (0–100) for each item:
- Build a token set from role keywords, plus keywords extracted from the pasted JD (lower-cased, stop-words removed, 1–3-word phrases appearing in JD, capped at 40).
- Text match 45%: weighted keyword hits in title (×2) + description. Technology/skills match 35%: overlap of `technologies` (projects) or `skills`+`name` (certifications) with `tech`+JD terms. Role-core match 10%. Recency 10% (newer = higher; certifications past `expiry_date` get 0 here).
- Weights are starting values in one exported constant so they can be tuned later; do not present them as scientific.
- Return `{ score, band, matched: string[] }`. Band: ≥60 High, 30–59 Medium, else Low. The UI shows `matched` as the reason. Do not call an LLM for ranking.
- Write unit tests (Vitest is fine to add as a devDependency) for at least: Cybersecurity vs frontend project ordering, JD terms boosting an item, expired cert not outranking a valid one.
